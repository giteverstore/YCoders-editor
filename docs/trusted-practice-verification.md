# Trusted Practice verification boundary

Future immutable Practice publications may include `content.trustedVerification`: versioned private executable tests and explicit timeout, memory, and output limits. The full immutable artifact remains available only to trusted publication services. `adaptPractice` and Practice delivery expose only the existing public-test projection and fail safety checks if trusted material enters a learner DTO.

`PracticeVerificationService` accepts a verified server principal separately from a strict browser submission. The submission cannot contain a learner UID, expected output, tests, reference solution, pass flag, or reward. The service resolves the exact `contentId + publicationVersion`, creates the server-only projection, optionally verifies a canonical Challenge assignment binding, and calls an `IsolatedPracticeExecutor`. Only a private-test pass creates an internal receipt tied to learner, version, policy, assignment, and immutable document hash.

No production executor exists in this repository. Production activation must remain disabled with `ISOLATED_EXECUTION_SANDBOX_NOT_CONFIGURED`. A real implementation must run out of process in a sandboxed container/VM service with no ambient credentials, deny network access by default, support the closed language inventory, enforce wall-clock/CPU/memory/process/output limits, discard the filesystem after each run, authenticate service-to-service calls, and return bounded untrusted diagnostics. Vercel `eval`, `child_process`, browser results, and public-test-only success are explicitly not acceptable.

Challenge completion, +20 coins, Practice +5 suppression, streak/history/calendar mutation, and idempotency belong in the learner/backend transaction boundary. That transaction should use canonical assignment identity as its idempotency key and consume the trusted result in the same authenticated server request where possible. This Editor repository does not expose a verification endpoint or activate rewards.
